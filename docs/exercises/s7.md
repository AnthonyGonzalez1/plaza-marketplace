# Session 7 exercises: events and notifications

Read [docs/events.md](../events.md) first. Start the stack with `docker compose up --build`.
Useful places while you work:

- Email inbox (Mailpit): <http://localhost:8025>
- RabbitMQ management UI: <http://localhost:15672> (`plaza` / `plaza`)

## 1. Write a consumer handler: the "order received" email

**Context.** `store-api` already publishes `OrderPlaced` when checkout creates an order, but
`services/notification-service` ignores it on purpose. The places to change are marked with
`Exercise S7` comments, and there is one skipped test waiting.

**Task.**

1. In `src/notifications/email-templates.ts`, add a template for `OrderPlaced`: subject
   "Pedido recibido: …", the items, the total, and a sentence saying the units are reserved
   until the payment is made.
2. In `src/notifications/notification.service.ts`, send that email for `OrderPlaced`.
3. Un-skip the test and make it pass. Add one more: the same `OrderPlaced` event twice sends
   one email.

**Hints.** Copy the shape of the `OrderPaid` case. The idempotency (claim in Redis, release on
failure) is the same for every type: check whether you need new code for it at all.

**Check.**

```bash
cd services/notification-service
pnpm lint && pnpm typecheck && pnpm test
docker compose up -d --build notification-service
```

Buy something and look at the inbox: two emails for a paid order (received, then paid).

## 2. Break the mail server and follow a message

1. Stop the mail server: `docker compose stop mailpit`.
2. Buy and pay an order.
3. In the RabbitMQ UI open **Queues** and watch `notifications.order-events`,
   `...retry` and `...dlq` for about 30 seconds. Also `docker compose logs -f notification-service`.

Answer:

1. Through which queues does the message travel, and how many attempts are made?
2. Where does the message end up? Open it in the UI (**Get messages**): which headers describe
   what happened?
3. Start the mail server again. Does the email arrive by itself? What would you have to do to
   send it? (In the UI you can move messages from one queue to another.)
4. Why is a DLQ better than retrying forever, and better than dropping the message?

## 3. See the outbox doing its job

1. Stop the broker: `docker compose stop rabbitmq`.
2. Buy and pay an order. Does the purchase work? Does the order become `PAID`?
3. Look at the table:

   ```bash
   docker compose exec postgres psql -U plaza -d plaza \
     -c "SELECT seq, type, published_at FROM outbox_event ORDER BY seq DESC LIMIT 5"
   ```

4. Start the broker again (`docker compose start rabbitmq`), wait a few seconds and repeat the
   query. Check the inbox.

Answer:

1. What did `published_at` show before and after?
2. Without the outbox (publishing directly inside the request), what would the buyer have
   seen at step 2, or what would have been lost?
3. In `OutboxRelay.publishPending`, what happens to the rows if `waitForConfirmsOrDie` throws?
   Which annotation makes that happen?

## 4. Prove that a repeated event is harmless

In the RabbitMQ UI, open the exchange `plaza.events` and publish by hand a copy of an
`OrderPaid` message that was already processed (routing key `order.paid`, the same JSON body
with the same `eventId`; copy it from the `payload` column of `outbox_event`).

1. Does a second email arrive? Which log line of `notification-service` explains it?
2. Change only the `eventId` and publish again. What happens now, and why?
3. Where is the list of handled events kept, and what is its weakness?

## 5. Read the e2e test

Open `e2e/tests/purchase.spec.ts` and run it (`e2e/README.md`).

1. Why does the test wait for the "paid" text with a long timeout instead of sleeping a fixed
   number of seconds?
2. Why are there only a few e2e tests while the API has more than a hundred?
3. Make the test fail on purpose (change an expected text) and open the HTML report and the
   trace. What does the trace show that a normal test failure does not?
