# Session 5 exercises: checkout and concurrency

Read [docs/sql/checkout-concurrency.md](../sql/checkout-concurrency.md) first. The backend
tests need Docker running. Run one test class with:

```bash
cd services/store-api
./mvnw test -Dtest=CheckoutConcurrencyIntegrationTest
```

## 1. Break it: reproduce the overselling bug

**Context.** `StockRepository.reserve` checks and decrements the stock in one `UPDATE`. The
concurrency test launches 50 buyers for 10 units and expects exactly 10 orders.

**Task.** Temporarily rewrite `reserve` the naive way: one `SELECT available ...`, an `if` in
Java, then an `UPDATE inventory SET available = :newValue ...`. Run the concurrency test.

Answer:

1. How many orders were created for 10 units? Run it three times: is the number stable?
2. What is the final value of `available`? Why is it not negative even though far more than
   10 units were sold?
3. Why did `OrderApiIntegrationTest` (same code, no concurrency) keep passing?

Revert the change. Do not commit it.

## 2. Write the pessimistic version

**Task.** Add a second method to `StockRepository`:

```java
public boolean reserveWithRowLock(long productId, int quantity)
```

It must `SELECT available FROM inventory WHERE product_id = :productId FOR UPDATE`, decide in
Java, and then run a plain `UPDATE`. Point `OrderService` at it temporarily and run the
concurrency test: it must pass.

**Hints.** `FOR UPDATE` locks the selected row until the transaction ends; a second
transaction's `SELECT ... FOR UPDATE` on the same row waits. It only works because
`placeOrder` is `@Transactional`: think about what would happen without the annotation.

Answer:

1. Why does adding `FOR UPDATE` fix the naive version of exercise 1?
2. Which version holds the lock longer, and why does that matter in a flash sale?
3. Keep the method (with a comment saying it exists for comparison) or delete it; switch
   `OrderService` back to `reserve`.

## 3. See the lock with two terminals

Start the stack (`docker compose up -d`) and open two database shells:

```bash
docker compose exec postgres psql -U plaza -d plaza
```

| Step | Terminal A | Terminal B |
|---|---|---|
| 1 | `BEGIN;` | `BEGIN;` |
| 2 | `UPDATE inventory SET available = available - 1 WHERE product_id = 1 AND available >= 1;` | |
| 3 | | the same `UPDATE` |
| 4 | `COMMIT;` | |
| 5 | | `COMMIT;` |

Answer:

1. What does terminal B show at step 3, and what changes at step 4?
2. Set `available = 1` first and repeat. What does B print after A commits (`UPDATE 1` or
   `UPDATE 0`)? Which rule of PostgreSQL explains it?
3. Repeat with two products to cause a deadlock: A updates product 1 then 2, B updates 2 then
   1. Which error appears and in which terminal? Which line of `OrderService` prevents it?

are where this kind of code breaks.
