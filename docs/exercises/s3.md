# Session 3 exercises: Kubernetes

Do these with the local cluster running (`deploy/kind/up.sh`). Each one takes 10-20 minutes.
Useful commands while you work:

```bash
kubectl -n plaza get pods            # add -w to watch changes live
kubectl -n plaza describe pod <name> # the Events section at the bottom explains failures
kubectl -n plaza logs <name>
```

## 1. Add probes and resources to the web pod

**Context.** `store-api` has three probes and resource requests/limits
(`deploy/helm/plaza/templates/store-api.yaml`). The `web` Deployment has none: Kubernetes
considers its pod ready the moment the container starts and reserves no memory for it.

**Task.**

1. In `templates/web.yaml`, at the `Exercise S3` comment, add a `readinessProbe` and a
   `livenessProbe` that do an HTTP GET to `/` on the port named `http`.
2. In `values.yaml`, replace `web.resources: {}` with requests and a memory limit. nginx serving
   static files is small: start with `cpu: 25m`, `memory: 32Mi` and a `64Mi` limit.

**Hints.** Copy the shape of the probes from `store-api.yaml`. nginx starts in well under a
second, so no `startupProbe` is needed. Think about why the web probes should hit `/` and not
`/api/...`.

**Check.**

```bash
helm lint deploy/helm/plaza --values deploy/helm/plaza/values-local.yaml --strict
deploy/kind/up.sh
kubectl -n plaza describe pod -l app.kubernetes.io/component=web | grep -E "Liveness|Readiness|Limits|Requests" -A2
```

## 2. Break a probe on purpose and watch what Kubernetes does

**Task A: break readiness.** In `templates/store-api.yaml` change the readiness probe path to
`/actuator/health/does-not-exist`, run `deploy/kind/up.sh` (it will time out, that is the
point) and look at the pods in another terminal.

Answer before reverting:

1. What is the `READY` column of the new pod, and how many restarts does it have?
2. Is `http://plaza.localhost` still working? Which pod is answering, and why did Kubernetes
   keep it?
3. What does `kubectl -n plaza describe pod <new pod>` say in Events?

**Task B: break liveness.** Revert A. Now change the *liveness* probe path the same way and
deploy again.

4. What happens to the `RESTARTS` column over two minutes? What status appears eventually?
5. In one sentence each: what is readiness for, and what is liveness for?

Revert the change and deploy once more to leave the cluster healthy. Do not commit the broken
probes.

## 3. See self-healing and a rollback

1. Delete the API pod: `kubectl -n plaza delete pod -l app.kubernetes.io/component=store-api`.
   Watch with `kubectl -n plaza get pods -w`. Who created the replacement?
2. Delete the database pod: `kubectl -n plaza delete pod plaza-postgres-0`. When it comes
   back, is the catalog data still there? Which object kept it?
3. Run `helm -n plaza history plaza`, then `helm -n plaza rollback plaza 1`. What changed?
