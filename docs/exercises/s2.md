# Exercises for session S2

One coding task and one reading task. Read `docs/sql/catalog-search.md` first. Run the commands
from `services/store-api`.

## 1. Add the `inStock=true` filter

**Context.** `GET /api/v1/products` filters by store, category and price. Buyers also want to
hide sold-out products. Three seed products have 0 units, so `?inStock=true` must return 57 of
the 60. The test `ProductSearchApiIntegrationTest.filtersByInStock` is already written and
switched off with `@Disabled`.

**Task.** Follow one existing filter (for example `categoryId`) through the three layers and add
the new one next to it:

1. `ProductController.searchProducts`: a new optional parameter
   `@RequestParam(required = false) Boolean inStock`, passed to `ProductSearchCriteria.of`.
2. `ProductSearchCriteria`: a new field. Decide what `null` and `false` mean (suggestion: both
   mean "do not filter").
3. `ProductSearchRepository.where`: one more condition when the filter is on.
4. Update the calls to `ProductSearchCriteria.of` in the tests, remove `@Disabled` from
   `filtersByInStock`, and add one unit test to `ProductSearchCriteriaTest`.

**Hint.** The condition must work in both statements that use `where(...)`. The count query is
`SELECT count(*) FROM product p` and has no join to `inventory`, so a condition written as
`i.available > 0` breaks it. A subquery works in both:

```sql
EXISTS (SELECT 1 FROM inventory inv WHERE inv.product_id = p.id AND inv.available > 0)
```

This filter has no value to bind, so `filterParams` does not change.

**How to check.**

```bash
./mvnw spotless:apply
./mvnw verify
```

`verify` must end with `Failures: 0, Errors: 0` and one skipped test fewer than before. Then try
it by hand: `docker compose up --build` and open
<http://localhost:8080/api/v1/products?inStock=true&size=100> (`totalItems` must be 57).

**Think about it.** Why is the product with exactly 1 unit a problem waiting to happen if two
buyers see it "in stock" at the same time? (Session S5 is about that.) Would you add an index
for this filter? On which table and columns, and how would you prove that it helps?

## 2. Read a query plan

**Context.** In an interview you may be shown a plan and asked what the database is doing. Use
the two plans in section 5 of `docs/sql/catalog-search.md` ("Before: no index" and "After: GIN
index").

**Task.** Write your answers in your own notes (not in the repository), then compare them with
the explanations in that document.

1. In the "before" plan, which line shows that the whole table was read? How many rows did each
   process throw away, and how many processes were there?
2. In the "after" plan, there are two lines for the `product` table: `Bitmap Index Scan` and
   `Bitmap Heap Scan`. What does each one do, and why are both needed?
3. `Heap Blocks: exact=229` and `rows=229`. What does it mean that the two numbers are equal?
4. Both plans sort by rank, but one says `quicksort` and the other `top-N heapsort`. What allows
   the second one?
5. In the "after" plan, how many times was the `inventory` index searched, and why is that more
   than the 20 rows returned?
6. The search for "producto" does not use the index even though it exists. Explain why that is
   the right decision.
7. Estimated versus actual: find one node where `rows=` in the estimate (first parentheses) is
   different from the actual value (second parentheses). Is the difference big enough to worry?

**Hint.** Read a plan from the most indented node outwards. `cost=` is the planner's estimate in
arbitrary units; `actual time=` is measured in milliseconds; `loops=` multiplies the per-loop
numbers.

**How to check.** Reproduce one of the plans yourself with the script in section 8 of the same
document and confirm that your plan has the same shape (the times will differ on your machine).
Then run the same `EXPLAIN (ANALYZE, BUFFERS)` with `OFFSET 5000` on a search that matches many
rows (for example `producto`) and explain to yourself why it reads more than `OFFSET 0`.
