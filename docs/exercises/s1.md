# Exercises for session S1

Two small tasks to do by hand. Both are checked by the test suite, so you know when you are done.
Run everything from `services/store-api`.

## 1. Reject blank product names in the database

**Context.** `V1__create_store_and_product.sql` declares `name text NOT NULL`, but `NOT NULL`
still accepts `''` or `'   '`. A constraint in the database protects the data even if a future
endpoint forgets to validate. `SchemaIntegrationTest.rejectsProductWithBlankName` already
describes the expected behaviour, but it is switched off with `@Disabled` because the constraint
does not exist yet.

**Task.**

1. Create a **new** migration in `src/main/resources/db/migration/` with the next free version
   number: look at the highest `V<n>__` file there and use `n + 1` (for example
   `V3__product_name_not_blank.sql` if the last one is `V2`). Do not edit `V1`: an applied
   migration is never changed.
2. In it, add a `CHECK` constraint named `ck_product_name_not_blank` to the `product` table.
3. Remove the `@Disabled` line (and the unused import) from `rejectsProductWithBlankName`.

**Hint.** `ALTER TABLE ... ADD CONSTRAINT ... CHECK (...)`. The condition must be true for valid
rows: `char_length(trim(name)) > 0`.

**How to check.**

```bash
./mvnw test -Dtest=SchemaIntegrationTest
```

It must report `Failures: 0, Errors: 0, Skipped: 0` (before the exercise it says `Skipped: 1`).

**Think about it.** What happens to this migration if a row with a blank name already exists?
Why is the constraint named instead of letting PostgreSQL pick a name?

## 2. Test that `size=101` is rejected

**Context.** `PageParams` limits `size` to 100 so that nobody can ask for the whole table in one
request. `PageParamsTest` covers the rule as a unit test, but no test proves that the HTTP
endpoint answers `400` with a problem detail.

**Task.** In `ProductApiIntegrationTest`, next to the `// Exercise S1` comment, add a test that
calls `GET /api/v1/products?size=101` and asserts:

- the status is `400`;
- the content type is `application/problem+json`;
- `$.detail` is `size must be between 1 and 100, but was 101`.

**Hint.** Copy `negativePageReturns400ProblemDetail` and change the parameter and the message.

**How to check.**

```bash
./mvnw test -Dtest=ProductApiIntegrationTest
./mvnw spotless:apply
```

The first command must show one more test than before, all passing. Then change the limit in
`PageParams.MAX_SIZE` to 200 for a moment and confirm that your test fails: a test that cannot
fail proves nothing. Put the limit back.

**Think about it.** Why validate `size` in Java instead of with a database constraint? What is
the difference between this kind of rule and the blank-name rule of exercise 1?
