## 1. Test the whole state machine

**Context.** `OrderStatus.canTransitionTo` holds the rule "only a pending order can become
paid or cancelled". `OrderStatusTest` checks 2 of the 9 combinations.

**Task.** Add one parameterized test that covers the 3 x 3 table (from, to, expected).

**Hints.** JUnit 5: `@ParameterizedTest` with `@CsvSource({"PENDING_PAYMENT, PAID, true", ...})`
and a method `(OrderStatus from, OrderStatus to, boolean expected)`. JUnit converts the text
to the enum by itself. Include the "same state" cases (`PAID -> PAID`).

**Check.** 9 rows, all green. Then change the rule on purpose (allow `PAID -> CANCELLED`) and
confirm exactly one row fails. Revert.

## 2. Forge a webhook

Start the stack (`docker compose up -d`), create an order from the web app and copy its id
from the URL.

1. Send an unsigned "approved" event:

   ```bash
   curl -i -X POST http://localhost:8080/api/v1/webhooks/payments \
     -H 'Content-Type: application/json' \
     -d '{"eventId":"11111111-1111-4111-8111-111111111111","orderId":"<id>","status":"APPROVED","amount":1}'
   ```

   Which status code comes back? Did the order change?

2. Now sign it yourself with the local secret and send it again with the header:

   ```bash
   BODY='{"eventId":"11111111-1111-4111-8111-111111111111","orderId":"<id>","status":"APPROVED","amount":<total>,"currency":"COP"}'
   SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac local-dev-webhook-secret | sed 's/^.* //')
   curl -i -X POST http://localhost:8080/api/v1/webhooks/payments \
     -H 'Content-Type: application/json' -H "X-Plaza-Signature: sha256=$SIG" -d "$BODY"
   ```

   What is the result now? Send exactly the same request again: what does the answer say?

Answer:

1. Step 2 worked because you know the secret. What does that tell you about where the secret
   must live and who may read it? Where is it configured in production
   (`docs/deploy.md`, `deploy/helm/plaza/templates/config.yaml`)?
2. Change one character of `BODY` but keep the old `SIG`. Why is it rejected?
3. Why does the code verify the signature **before** parsing the JSON?

## 3. Watch duplicates being ignored

```bash
PLAZA_PAYMENT_DUPLICATE_WEBHOOKS=true docker compose up -d payment-simulator
docker compose logs -f store-api
```

Pay an order with the "declined" button and read the log.

1. How many times did the webhook arrive, and how many times was the stock returned?
2. In `ProcessedWebhookRepository`, why is the check an `INSERT ... ON CONFLICT DO NOTHING`
   and not a `SELECT` followed by an `INSERT`? (Same idea as session 5.)
3. In `PaymentService.handle`, what would go wrong if recording the event and changing the
   order were in two separate transactions and the second one failed?

## 4. Look at the expiry query plan

Open a database shell (`docker compose exec postgres psql -U plaza -d plaza`) and run:

```sql
EXPLAIN SELECT id FROM orders WHERE status = 'PENDING_PAYMENT' AND expires_at < now();
\d orders
```

1. Which index does the table have for this query, and what is special about its definition?
2. With only a few rows PostgreSQL may still choose a sequential scan. Why is that the right
   choice for a tiny table?
3. Why would a normal index on `(status, expires_at)` grow forever while this one stays small?

## 5. Idempotency by hand

With curl, create a cart with one product and send the same `POST /api/v1/orders` twice with
the header `Idempotency-Key: my-test-1`. Compare the two order ids and the stock. Then repeat
without the header: what happens on the second request, and why is that only a partial
protection?
